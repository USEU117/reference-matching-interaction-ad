## 1. 一页速览

### 1.1 项目一句话

少样本工业异常定位。四条分支（B=DINOv2-B/14、S=DINOv2-S/14、C=AnomalyCLIP ViT-L/14@336 视觉描述子、D=WideResNet50-2）在**冻结的参考块融合**下，研究一个因子化交互：
**「新增/替换视觉表征分支」的收益是否取决于「正常参考的匹配方式」**。
`J` = 各分支共同选一个参考 patch 行；`L` = 各分支各自找最近参考行；`E = P(新表征) − P(对照)`；`I = E_L − E_J`（论文主线量，stride-8 像素 AP，类别宏平均）。
当前论文标题方向见 `docs/manuscript_reference_matching_20260914/English_Manuscript_Source.md`（正文 8 图 / 17 表，元数据见 `build_validation.json`）。

## 5. 踩过的坑（最重要的一节）

> 每条：**症状 → 根因 → 处置**。前 4 条是本项目特有的、最容易重复踩的。

### 坑 1：Windows PowerShell 5.1 把无 BOM 的 `.ps1` 按 GBK 解码；`1>>` 写 UTF-16LE

- **症状**：编排脚本**完全无法解析**（27 个 parse error，报"缺少 )"、"意外的标记"）；或日志解析**全空**。
- **根因**：PS 5.1 对**无 BOM** 的 `.ps1` 按 ANSI/GBK 解码，脚本里的中文被拆成坏字节 → 引号/反引号失配。另一路：`1>>` 重定向在 PS 5.1 下写 **UTF-16LE**，下游按 UTF-8 解析只能得到空行。
- **处置**：**所有 `.ps1` 一律纯 ASCII**（中文交给 Python 脚本，Python 默认按 UTF-8 读源码）。自查：`[IO.File]::ReadAllBytes($p) | Where-Object {$_ -gt 127}` 必须为 0；`_night2_20260918/PS_PARSE_CHECK.json` 记录了 `parse_errors: 0 / non_ascii_bytes: 0`。改脚本后先做**只解析不执行**的语法自检：
  ```powershell
  foreach($f in @('run_analysis.ps1','night_run_2_20260918.ps1')){
    $errs=@(); $tokens=@()
    [void][System.Management.Automation.Language.Parser]::ParseFile(
      (Resolve-Path "scripts\limitation_closure_20260915\$f").Path, [ref]$tokens, [ref]$errs)
    "{0,-28} parse errors = {1}" -f $f, $errs.Count
  }
  ```

### 坑 2：无 BOM 的 UTF-8 gate JSON 被 PS 5.1 按 GBK 读 → 门禁假阴性

- **症状**：门禁判 FAILED，但人工打开 JSON 看字段明明是通过。
- **根因**：Python 写出的 gate JSON 是**无 BOM 的 UTF-8**；PS 5.1 用 `Get-Content -Raw | ConvertFrom-Json` 会按 ANSI/GBK 解码（含中文或非 ASCII 字节时直接崩或读歪）。
- **处置**：PS 侧读 JSON 一律显式 `-Encoding UTF8` 或用 `[IO.File]::ReadAllText($p,[Text.Encoding]::UTF8)`；反过来，PS 写的 JSON 会**带 BOM**，Python 侧必须 `encoding="utf-8-sig"`（例如 `seeds_extension_20260917/ANALYSIS_CHAIN.json` 就带 BOM，用默认 `utf-8` 一读就 `Unexpected UTF-8 BOM`）。`night2_reconcile_gate_status.py` / `night2_refresh_gate_snapshots.py` 就是为修这个假阴性写的。

### 坑 3：并发资源竞争伪装成"网络挂起"（含守护脚本误杀健康进程）

- **症状**：AnomalyDINO 的 VisA dump 反复"挂死"（进程 CPU 恒 0，最长一次 2 小时），看起来像网络问题。
- **根因**：不是网络。真实主因是**与另一个峰值 5–8 GB 的 CPU 作业并发时的资源竞争**；机器空闲时同一条命令 **22 分钟**就跑完 visa canvas（48/48）。另一处独立缺陷：守护脚本 `scripts\limitation_closure_20260915\anomalydino_guarded_retry.ps1` 用 `Start-Process -PassThru` 的 `TotalProcessorTime` 判断停滞，会把**刚启动、尚未累计 CPU 的进程误读为 0**，从而**误杀健康进程**（至少误杀两次）。
- **处置**：先确认机器是否空闲再重试；守护判据改用**日志 mtime 或增大预热窗口**，不要把它当"网络问题探测器"。同时在 `methods/anomalydino/src/backbones.py` 的 `load_model()` 里改为优先 `skip_validation=True`（见坑 4），并**如实记录**"补丁不是当时唯一失败原因"。完整订正见 `_night2_20260918/VENDORED_PATCH_anomalydino_backbones.md`。

### 坑 4：`torch.hub` 复用缓存仍联网校验（无超时）→ vendored 补丁

- **症状**：`torch.hub.load('facebookresearch/dinov2', ...)` 在**本地缓存已存在**时仍会向 GitHub API 发 fork 校验请求（`_validate_not_a_forked_repo`），该请求**没有超时**；本机到 GitHub 的路径不稳定 ⇒ 挂死或 `RemoteDisconnected`。
- **根因**：`torch.hub` 的默认行为。
- **处置**：vendored 代码（**`methods/` 被 `.gitignore` 排除，补丁无法用 git 记录**）改为
  ```python
  try:
      model = torch.hub.load('facebookresearch/dinov2', self.model_name, skip_validation=True)
  except TypeError:
      model = torch.hub.load('facebookresearch/dinov2', self.model_name)
  ```
  只跳过那一次 fork 校验，**权重完全不变**（实测 6.3 s 加载，`patch=14`）。补丁内容与验证方式单独存档：`_night2_20260918/VENDORED_PATCH_anomalydino_backbones.md`（因为 `git ls-files methods` 只有 2 个历史遗留文件）。复现 dump 命令也在该文件里。

### 坑 5：快估计器与慢实现的等价性门（1e-15）与其适用位置

- **事实**：`scripts/limitation_closure_20260915/` 有一条"快估计器"路径（`s4_extra_encoders.py --fast-replicates`）；夜跑阶段 1 的门 `_night2_20260918/FAST_ESTIMATOR_PARITY.json` 实测 **`max_abs_delta = 1.221e-15`（阈值 1e-9，288 单元）**，`FAST_PARITY_KSDD2.json` 在 KSDD2 真单元上 R=20、逐副本 max|Δ| **9.99e-16**（阈值 1e-12）。
- **适用位置**：只有"逐副本重算昂贵、但点估计已冻结"的阶段才允许用快估计器（K 扩展后的 E1/E2/E3 表刷新、matched/wide 重算）；**首次产生方法的阶段不得用它**。
- **处置**：任何新用途都要先跑对应的 parity 门（1e-15 量级才放行），并把门结果落盘。

### 坑 6：聚合层错配（宏平均 vs 单类别）导致假"回归失败"

- **症状**：d3 的 VD.3 回归门自报 `false`、差值 0.032。
- **根因**：把**已发布的"数据集宏平均"**与**单个类别**的值相比。
- **处置**：改为**宏对宏**后 `max|Δ| = 2.60e-18`（mpdd）/ `6.72e-18`（btad），`tolerance_1e_9=true`；原先的 0.032 / 0.007 保留为 `per_category_max_abs_delta` 以示区别（`d3_seed_variance.py`、`interaction_seed_variance.json → VD_3_regression`）。旧交接 §D.7 的"远大于 1e-9 就先别写进论文"这条约束**已解除**。

### 坑 7：`--skip-existing` 分支不重发聚合行 → 聚合表被截断

- **症状**：`05_extra_encoders/E1|E3/new_method_metrics.csv` 只有 **5 字节**（表头），VE.2 证据缺失。

### 坑 10：内存/并发预算必须按"峰值之和"算

- 16 GB 机器上 8 个 stats worker（≈6.4 GB）+ E3 + d3 + 3 个 fullpixel（各 1–2 GB）超配，两个 fullpixel 被 `_ArrayMemoryError` 打死（差 136–196 MiB）。
